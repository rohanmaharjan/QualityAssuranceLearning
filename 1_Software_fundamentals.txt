What is software testing?
Software testing is the process of evaluating software to find defects and verify that it behaves according to specified requirements.
Testing = checking whether the software does what it is supposed to do, and discovering what it does wrong.

Verification Vs Validation
# Verification
  "Are we building the product right?"
  It checks whether the software is being developed according to specifications/designs/requirements.
  Reviewing requirements, reviewing design documents, code reviews, documentation reviews

# Validation
  "Are we building the right product?"
  It checks whether the actual software satisfies the user's needs and requirements.
  Runnign login tests, testing checkout, testing registration, testing APIs

QA vs Testing
# QA (focuses on preventing problems)
  It is process-oriented.
  Its goal is to prevent defects and improve the software development process.
  Defining testing processes, establishing coding/testing standards, process improvemnt, reviewing development practices

# Testing (focuses on finding problems)
  It is product-oriented.
  Its goal is to find the defects in the actual software.

    • are error messages understandable?
    • does the page work on mobile?
    • does pressing enter submit the form?

Important Note:
    Don't think onl: "What should I test?"

    Also think: "What can go wrong?"

For exmaple:

What is Defect/Bug?
A defect is a problem in the software where the actual behavior differs from the expected behavior or requirement.

Example:
Password must contain at least 8 characters.
You enter Password: abcd
The application allows you to log in.

Error vs Bug
    Error: A mistake made by a person.
        Develper writes > instead of >=
    Defect/Bug: The mistake in the software.
    Failure: the software actually behaves incorrectly when the defect is executed.

Expected vs Actual Result
    Requirement: Ater successful login, the user should be redirected to /dashboard.
    Test: Enter valid credential and click login button.
    Expected: User is redirected to the dashboard.
    Actual: User remains on the login page.

Test scenario (What to test?) vs Test case (How exactly we test?)
    Test scenario: A high-level thing you want to test.
    Example: Test login functionality.

    Test case: A specific set of steps, inputs, and expected results used to verify something.
    Example:
    Verify login with valid credentials

    Precondition:
    User has a registered account.

    Steps:
    1. Open login page.
    2. Enter registered email.
    3. Enter correct password.
    4. Click Login.

    Expected:
    User is redirected to dashboard.

Functional (What it does?) vs Non-Functional (How well it does?) Testing
Functional Testing: Tests what the system does.
    Example: Does clicking Login authenticate the user?
    Login, Registration, Search, Checkout, Payment, Password registered

Non-Functional testing: Tests how well the system performs.
    Example: Performance (Can 10000 users access aplication simultaneously?)
             Security (Can an authorised user access anouther user's account?)
             Usability (Can users easily understand the interfac?)
             Compatibility (Does the application work on different browser and devices?)
             Reliability (Does the system remain sable for long periods?)

Black Box tesing vs White Box Testing
Black Box testing: You test the software without knowing its internal code/implementation.
    Example: Input --> Login application --> Output
    you dont care if it is devloped using Py, JS, C++, and only care about behaviour of the system
    Manual functional testing is often black-box testing.

White Box testing: You have knowledge of the internal implementation/code.
    Example: 
    if password == stored_password:
        login()
    Developers commonly perform a lot of white-box testing through unit tests.

Grey Box Testing: YOU hav paratial knowledge of the internal system (API architecture, Database structure, Authentication mechanism)

Manual Testing vs Automation Testing
Manual testing: A human performs the test
    Open browser --> Enter email --> enter password --> click login --> check results

Automation testing: A program performs the testing.
    automation script --> open browser --> enter credentials --> click login --> verify dashboard

Note: Automation is excellent for repetitive tasks, while it doesnt replace QA thinking.

Smoke Testing
Imagine developers deploy a new build.
Before spending 5 hours testing every feature, QA first asks:
"Is this build stable enough to test?"
That's where Smoke Testing comes in.
Example:
    can application open? --> can user login? --> can user search? --> can product be added to the cart? --> can checkout open?

    if the lofin itself is completely broken, there'value in spending hours testing advanced features.

    Therefore, Smoke testing is a set of basic tests performed to verify that the major functionality of a build is working and that the build is stable enough for further testing. 

Sanity Testing:
Now imagine developers fix one specific bug:
"Checkout discount calculation was incorrect."
A new build is provided.
You don't necessarily test the entire application from scratch.
Does the Particular change/fix work correctly?


Retesting vs Regression testing
Suppose there's a bug:
    Login fails with a valid password.
Developer fixes it.

Retesting: You test that eact bug again.
    Previously failed test --> Developer fixed bug -- > Run same test again
    Purpose: Verify that the specific defect has been fixed.

Regression: You test other existing functionality to ensure the fix didn't break anything else.
    Purpose: Did the fix break something else?


# Testing
A) Unit Testing
    Tsting the smallest individual component of the software in isolation.
    Example: A backend has:
      validate_email()
      check_password()
      authenticate_user()
      create_session()
    A developer might test:
      validatee_email()
      for this database, frontend, and other components arent necessarily involved.

B) Integration Testing
    Now we combine multiple components and check whether they work correctly together.
    Example: For login
    Frontend --> Login API --> Authentication service --> Database
    even though each component work individually, they may not work together if they dont communicate correctly.

    user enters username and password.
    frontend sends the request --> API receives it --> API queries databse --> data base return user --> API responds --> frontend redirects

C) System Testing
    Now we test the complete integrated application as a whole.
    Example: for an e-commerce website
    login --> search --> product --> cart --> checkout --> payment --> order --> email confimation
    we're testing the complete system against its requirements.

D) Acceptance testing
   Now we ask:
        "Does this system satisfy the business/user requirements well enough to be accepted?"
    This is often associated with UAT — User Acceptance Testing.
    For example, an e-commerce client requested:
    Users must be able to purchase products using credit cards.
    The system may technically work, but the business/user needs to verify that it actually satisfies their requirements. 

Static vs Dynamic Testing
    Static Testing
    Static testing means testing without executing the software.
    It involves reviewing Requirements, design documents, test palns, soource code, and documentation
    Example:
    Suppose the requirement says:
        "Password must contain at least 8 characters."
    During a requirement review, you notice that another document says:
        "Password must contain at least 6 characters."
    You can identify this inconsistency before the application is even built. This is called static testing.

    Static testing techniques:
    Review: People examine a document/code to find issues.
    Walkthrough: The author walks others through the document/code.
    Inspection: A formal, structured review designed to identify defects.
    Stati analysis: Tools analyze source code without executing it.

    Dynamic Testing:
    Dynamic testing involves executing the software and observing its behavior.
    Its like running the application.
    Example: Open login page --> enter email --> enter password --> click login --> observer Result


Test Design techniques
A) Equivalence Partitioning
    suppose age must be between 18 and 60.
    A beginer might test 18,19,20,21,....60; that's unnecessary.
    Instead divide the possible inputs into groups/classes where the system should behave similarly.

    Valid Partition: 18-60
    Invalid Partition: <18 and >60

    instead of testing many values, we could select representatives like below valid range, valid range and above valid range.
    
    we assume values of same partition will behave similarly.

B) Boundaray value analysis
    it specifically focuses on the edges.
    exmaple: age = 18-60
    The important values are 17, 18, 19, 59, 60 ,61
    this is usefull as programmers ususlly amkes mistakes around boundaries.
    if age>18: instead of if age>=18:
    
C) Decision Table testing
    Now imagine a login system with these rules:   
    Email must be registered.
    Password must be correct.
    Account must be active.

    A user's login result depends on multiple conditions simultaneously.
    This is where Decision Table Testing becomes useful.

    We create conditions:
    Condition	C1
    Registered email?	Yes/No
    Correct password?	Yes/No
    Account active?	Yes/No

    Then determine the expected result.
    It becomes especially useful when there are many combinations of conditions.

    They are used when requirements contain AND, OR, multiple conditions, discounts, permissions, authentication rules

D) state transition testing
    Some systems don't simply have:
    Input → Output
    Instead, the system can exist in different states, and an action causes it to move from one state to another.
    That's called State Transition Testing.

    Example: Banking system
    Active --> Withdraw --> Active

    But suppose the user enters the wrong PIN three times:
    Active --> Wrong PIN --> Wrong PIN --> Wrong PIN --> Locked

    Entering fourth PIN shouldn't behave as the first incorrect PIN.

    Wrong --> Wrong --> Right --> Wrong --> Wrong
    If the requirement says "3 consecutive failed attempts", it should not lock the account after the third wrong attempt overall, because the successful login reset the consecutive-failure count.

E) Use case Testing
    A use case describes how a user interacts with a system to accomplish a goal.
    For example:
    Use case: User logs into the application.
    Basic Flow: Open login page --> Enters mail --> nter password --> clicks login --> system validiates credentials --> dashboard
    this is the peimary flow but it is also important to consider alternative flow (incorect credentials) and exceptional flow (database not available).

F) Error Guessing
    Error Guessing means using your experience and intuition to predict where defects are likely to occur.
    There isn't necessarily a formal formula.

    You ask:
    "Where would a developer probably make a mistake?"

    For a login form you might test, empty feilds, spaces, very long input, special passwords, wrong password, case sensitivity, copy/paste, rapid repeated clicks, browser back button, refresh after login, session
    These are common places where software can behave unexpectedly.

G) Exploratory testing
    Instead of following only predefined test cases, you:
    Learn about the application, design tests, and execute them simultaneously.
    You explore the application and follow interesting behavior.

    Example: 
    open website --> try normal login --> notice unusual error --> investigate error --> try different input --> discover another behaviour --> investigate further
    Exploratory testing is an approach where learning about the application, designing tests, and executing tests happen simultaneously rather than strictly following predefined test cases.
